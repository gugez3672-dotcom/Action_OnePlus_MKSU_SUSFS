# 构建完成到实际部署之间的门槛

此文件记录后续必须解决的交付问题，不是新的刷写/安装授权。本轮不连接手机、不刷写、不预装模块。

## 内核和管理器同时准备

必须先有正式 D2.0.0/36200 与配套官方 ksud/ksu_susfs，通过包名/证书、协议、后端哈希及静态特征审计，再确定升级次序。D1.1.1 被新内核识别为管理器不等于旧 SukiSU 协议后端可用；D2 未齐不能先刷内核。

## 启动链和回退

先核对实机身份、活动槽、K32 boot 与 init_boot，以及 `/data/adb` 的完整备份与哈希。B 槽不作为可靠回退槽。USB fastboot/离线恢复由用户在场配合，不能把远程隧道作为唯一入口。

首轮审查认为“K32 PGuard 会拦截 AnyKernel 写 boot”，该推断与现有证据冲突：`协作/设备现状.md` 手机摘要记载 boot/boot_a/boot_b 放行；K32 封存 `PLK110_PGuard_v2_source.c` 第56–58行也明确放行 raw boot 以便本地 AnyKernel 升级。因此不把 AnyKernel 必然被拦写作为既定事实。实际刷入方式待核对实机及安装包脚本后定，仍可按完整 boot.img + USB fastboot 方案准备；本轮没有试写。

当前记录中 init_boot_a 仍为旧 SukiSU LKM。新内置官方 KSU 下的重复加载风险需要解决；恢复为 A67 官方原版的具体镜像、操作分区、顺序和回滚仍须按桌面索引/实机与用户确认，不能仅凭此审查自动刷入。

## 模块挂载和授权数据

逐项核对实机模块与实际文件/脚本，区分需要 system 挂载的模块和纯脚本模块。官方 metamodule 仅对需要挂载的功能构成依赖；先选择兼容实现再形成部署方案，不自动安装。固定官方源码的 metamodule 文档及 FAQ 已核对，详见 `D2-port-contract.md`。

备份并比较旧 allowlist/app profile 与官方格式，记录各用户及 shell(2000) 的授权，明确可迁移和必须重新授权的项目。准备本地重新授权、官方 ksud 初始化、模块禁用/恢复及回退步骤，不能假定远程 Root/ADB 在切换后仍可用。

### 元模块核对表（部署前填写，当前未读取实机）

| 每个模块记录 | 要判断什么 |
|---|---|
| 物理目录 / 声明 ID / 版本 / 禁用、更新、移除标记 | 操作目录不能从 module.prop 声明 ID 推断；待重启状态不等于已生效 |
| system/、skip_mount 与实际脚本 | 系统覆盖是否依赖元模块；不能把无 system/ 直接写成完全不挂载 |
| post-fs-data、post-mount、service、boot-completed | 与新挂载阶段是否兼容，统计原值采集是否发生在挂载前 |
| Zygisk、其他模块、旧框架私有命令和环境 | 依赖能否被官方后端支持；不支持项先禁用，不直接整包重放旧配置 |
| 元模块版本 / 实现 / 挂载来源 / 重启后挂载与进程命名空间 | 只有一个元模块；overlayfs 与 Magic Mount 选择需依据模块需求和实际内核能力 |

官方元模块要求的挂载来源 `KSU` 属于兼容接口，不因管理器改名而替换；能在 `/proc/mounts` 中看到什么以及 SUSFS 隐藏是否有效，必须在目标进程上下文实测。卸载、停用、更换元模块会影响其他模块的挂载，先准备整体恢复路径。管理器依赖面板只描述安装目录，不宣称内核实际挂载已通过。

新文件系统配置位于 `/data/adb/daily-notes/filesystem`，通用 early/late hook 分别在 post-fs-data.d、post-mount.d。部署前核对旧脚本是否会重复写同一 SUSFS 项；安全模式、禁用和回退时须把这两处通用 hook 一起纳入备份/恢复，不能仅停用元模块后认为全部配置都已停用。导入旧配置需先校验 schema v2，日志选项不可启用，统计新增/删除/全局关闭等项目按界面提示重启核对。

## 已明确的范围

用户本轮已确认这一版不带 PGuard，稳定后再独立考虑分区保护及 `/dev/sg*` 覆盖。该选择不改变现有设备状态；上机后要分别记录新内核/管理器安装、重启、Root、模块、SUSFS、ADB 门控、检测与稳定性验收。
